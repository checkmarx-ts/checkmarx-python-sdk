* [Add] get_package_remediation_for_cve on PackageRisksAPI for GET /api/v1/Packages/{type}/{name}/{packageVersion}/remediation/{cve} on the SCA Data Hub service -- upgrade recommendations (latest/nearest/current, each with per-severity vuln counts) for one package version with respect to one CVE. Reuses the PackageVersionRemediation DTO already modeled for get_package_risks's `remediation` field, which matches this response exactly -- confirmed by live test against a real tenant, including a 404 for an unknown CVE and a scoped npm package name (`@babel/core`, containing a reserved `/`) to verify path-segment URL-encoding.
* [Add] PackageRisksAPI (get_package_risks) for POST /api/v1/Packages/risks on the SCA Data Hub service -- retrieves vulnerability and suspected-malware risk data for up to 100 package versions per request, identified either by pURL or by type/name/version. New config field `datahub_base_url` (CxOne config key `datahub_server`, default https://us.datahub.sca.checkmarx.net) since this service lives on its own host but shares CxOne auth (verified live: the main CxOne tenant's token is accepted as-is). 16 new DTOs. Live-verified against a real tenant, and the actual response shape differs substantially from the public API reference: `status`/`isDeprecated`/`remediation`/etc. are nested inside `package`, not siblings of it; each vulnerability's `id`/`cve`/`cxId`/`revision`/`score`/`severity` are top-level fields sitting alongside `details` (not inside it as the doc implies), with `details` instead holding a much richer object (description, CWE, CVSS3/CVSS4, EPSS, references, affected paths, CPEs) only populated when IncludeRiskDetails=true; `remediation` has a concrete latest/nearest/current shape. Modeled all of this from the live data. `suspected_malware`'s sub-schema remains unverified (no live example tripped it, including a known-malicious npm version) and is flagged as such in the DTO docstring.
